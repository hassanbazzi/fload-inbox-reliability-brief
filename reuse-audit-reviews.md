# FLO-1355 review execution reuse audit

Date: 2026-09-21. Read-only source audit; no provider calls, database inspection, migration execution, or implementation changes.

Compared feature HEAD `d0945bb3ca61370e3d783d4fcec9573f58d66e01` with locally available `origin/main` `b5253b2d799cf35863a9d0c31e3481762e44afde`. Also inspected the preserved, uncommitted browser lifetime and 0175 execution work separately. References below are repository-relative paths and one-based lines in the working source at audit time; an explicit **main** reference means `git show origin/main:<path>`. Working line numbers can move when the saved work is consolidated.

## Findings that change the implementation plan

1. **The existing headless SRP path is a real reusable HTTP transport. A new private Chromium stack is not required merely to address an original-store review ID.** Main already has `WebSession.request`, `json`, `switchProvider`, cookie caching, SRP/2FA, sticky proxy routing, and production wiring. The new private review runner explicitly disables that manager and forces fresh browser login. That default should be removed from the proposed review execution architecture.
2. **Current review delivery is API-first, with a reachable cookie/WebObjects fallback.** Individual keys are provisioned during invitation setup. This is neither an all-browser system nor an API-only system by source inspection. No production traffic/credential census was performed, so this audit cannot say how often fallback executes.
3. **Existing approval guards, queue receipts, delivery claims, and applied verification are substantive capabilities, not missing foundations.** Reuse them and their provider clients. Their limitations are narrower: process-local grants; loss of exact approving ticket at the queued transport boundary; expiring draft claims without immutable per-interaction results; post-call logging; and verification bound to mutable review/work anchors. Durable Actions attempts and evidence address those gaps; rebuilding authentication does not.
4. **The feature currently has parallel execution authority and recovery systems.** New Actions code calls the new native write method through its own admission/completion owners. Existing production uses `guarded-review-reply`/`executeGuarded` plus draft drains and the applied-verification ladder. The old write-boundary test does not cover the new package-native path. These cannot both remain independent active authorities for the same obligation.
5. **The Actions global resource guard does not fence an unchanged legacy sender.** Legacy sends claim a draft and consume a process grant, while Actions locks its own resource row. Activation needs one owner or an exclusive, enforced handoff; new guard correctness alone does not make coexistence safe.
6. **The native identity issue is real, but independent of browser ownership.** Existing official-API bridging can select the first same-text/rating/nickname match. The new API source uses API resource IDs; the new WebObjects source uses original-store IDs. A canonical hash does not prove those are the same review. Keep this limitation explicit; it does not establish a need for another login stack or a second recovery implementation.

## Existing individual keys and SRP: preserve these owners

### Official API credentials

- `services/worker/scraping/invitation-acceptance.ts:485–488` already provisions an individual key after accepting an invitation. Provisioning is nonfatal; the source may remain scraper-backed.
- `connectors/app-store-connect/api-capabilities.ts:29–42` selects a validated individual key or a complete team key. `services/asc-individual-key.service.ts:27–49` builds the existing client from those credentials.
- `packages/apple/src/app-store-connect-api/client.ts:299` prefers the individual key, then team key. The added secret-free `getCredentialPrincipal` at 294 is a useful binding to the **same signer snapshot**, not a reason to create another credential service.
- The legacy sender's individual-only resolver is narrower than the general loader. Consolidating the source owner should resolve this deliberate behavior explicitly, not silently infer that team fallback is already used everywhere.

### Headless SRP transport, already on main

- **Main** `apps/api/src/connectors/app-store-connect/web-session/web-session-io.ts:187` wires `WebSessionManager` to encrypted Redis cookies, the existing login lock, `UndiciAppleTransport`, Redis/Twilio 2FA and the widget-key store. Account loading and sticky proxy provenance are at 159–183. Cookie cache lifetime is at 28.
- `packages/apple/src/app-store-connect-web/web-session.ts:92` exposes authenticated raw HTTP `request`; 107 provides JSON/CSRF requests; 130 implements provider switching; 170 performs fresh SRP and 2FA; 245 reuses validated cached sessions or serializes login. These implementations exist on main.
- `packages/apple/src/app-store-connect-web/undici-transport.ts:31–66` sends one request through the cookie jar/sticky proxy and returns status, headers, **raw text**, and parsed JSON. It uses manual redirects. It is not Chromium.
- Existing `client.ts:1125` loads this manager, 1267 hydrates a browser from its cookies, and `ensureLoggedIn` at 1606 tries that path. This is a concrete current caller, not a hypothetical transport.

**Required narrow additions for strict review execution:** explicit cancellation/deadline propagation; bounded body consumption; parsing the retained raw text rather than already-rounded JSON; exact native principal/provider verification; and protection against concurrent provider switches on the same cookie session. Current `WebSession.request` has no signal parameter, `UndiciAppleTransport` reads the whole text, and the main Redis lock only serializes login (main IO file 67–82). None of these deficiencies requires replacing SRP/2FA/account loading. Extend the existing transport/ownership seam and use one provider-owned review decoder.

An SRP session making the selected WebObjects request is the concrete reuse direction, not a verified all-account compatibility claim. This audit made no native calls. Prove the adapter using retained/fake HTTP contracts first; any authorized provider read needed to establish WebObjects availability should be scoped separately. Never infer publication from a WebObjects acknowledgement or missing native pending state.

### New private Chromium default: redundant choice

`services/actions/providers/app-store-connect/review-browser-session.ts:135–174` constructs an ephemeral scraper, creates a page, and forces fresh login. `connectors/app-store-connect/app-store-connect-scraper.ts:138–142` explicitly throws when that private mode asks for the shared SRP manager. The new runner does retain meaningful post-call distinctions—native result versus uncertain session context, cleanup versus result, and interrupted callback versus no-send—but those are **operation/ownership semantics**, not a reason to disable the existing HTTP session implementation.

The common lifetime lease draft also touches the existing scraper and SRP IO. Reuse any proven compare-token/abort/cleanup primitive through the existing owner after review; do not integrate the broad runtime rewrite simply because the private-browser implementation required it. A native resource guard and a session-provider-switch lease protect different resources and must not be conflated.

## What existing reliability does and does not prove

The existing kernel is not a straw man. `execution-kernel.ts:203–251` freezes a grant, hashes canonical parameters, stores it in a private `WeakSet`, consumes it once, and validates the exact binding/TTL. `guarded-review-reply.ts:97–110` derives reply text from authorized fields. The system already has queue acknowledgement verification (`inbox-work/execution-receipt.ts:24`, 74), draft claims, readback booking compare-and-set, provider comparisons and alerting.

The missing durable guarantees are concrete:

- A process grant is not an immutable database attempt. A process crash loses the grant; logging follows the transport (`guarded-write.ts:590–600`).
- The queued review path currently reconstructs `connector_automation` lineage rather than the approving ticket. `reply-helpers.ts:390–407` documents the loss explicitly. Building a grant from the caller's current reply text does not recover that approval.
- Draft claim expiry makes a row eligible for another drain without distinguishing no-call from possible application. New late/conflict retention addresses a different question than timestamp compare-and-set.
- The current API fallback path can move to another transport after a failed call. The new strict attempt policy must not inherit that behavior.
- Existing verification uses mutable anchors: `reply-readback-scheduling.ts:58–80` documents republish/overwriting-verdict risks; `execution-log.ts:145–162` updates the verdict by execution ID without preserving a separate immutable observation for each read. New exact cycle/subject/observation history is useful here.
- Queue admission evidence (`reply_queued`) deliberately does not prove a native send. Keep that distinction instead of claiming the old receipt was already a native write receipt—or discarding it as worthless.

These are reasons to consolidate around a durable owner, not evidence that every new provider-specific service/table was necessary.

## Concrete consolidation and deletion order

1. **Keep new browser integration stopped.** Preserve 0175 and lifetime prototypes; do not register them or generate more browser tables. The current audit changes only this report.
2. **Choose one transport per exact admitted operation.** Prefer the existing validated API client for API-native targets. For retained original IDs, evaluate the existing SRP/WebObjects HTTP path with the strict decoder. No implicit API-to-WebObjects fallback after a call. Record unsupported identity mappings visibly.
3. **Make one authoritative review command/execution boundary.** Keep immutable Actions command/approval/attempt/evidence semantics where required. Bridge existing user/agent entrypoints into that owner with exact lineage, rather than running a second approval and delivery system. Adapt the existing guarded-write boundary/capability policy to the canonical admission, without a second independently mintable authority. Update boundary tests to include package methods.
4. **Reuse provider implementations.** Keep the existing individual-key signer and SRP manager. Add bounded one-shot HTTP/signal support and exact principal/source validation there. Reuse native review parsing/comparison where it is truthful. Remove forced private-browser construction and its review-only cache suppression; retain established browser functionality for unrelated callers.
5. **Cut over obligations exclusively.** A migrated review cannot remain eligible in the old draft drain or old verification ladder. Preserve historical queue receipts/drafts/readback results as evidence, with explicit handoff and no invented approval. Until this is implemented, new global-resource exclusivity is not a whole-system guarantee.
6. **Delete old review-only execution branches after handoff tests.** Candidates: `sendReplyPreferApi` automatic fallback; the old review delete/recreate retry helper when no unmigrated caller remains; connector-automation substitution for approved review work; review-specific old ladder scheduling for migrated obligations. Do not delete the general work-execution kernel, other capabilities' verification, or existing SRP/browser services used elsewhere.
7. **Delete new duplication after the transport choice.** Remove the private-Chromium default/second session lifecycle. Remove 0175 recipe/planner/storage additions from the merge candidate unless the selected WebObjects contract needs their distinct native facts; if it does, retain the minimal protocol leaf inside the common execution owner. Avoid mass migration rewriting until root decides the unactivated feature migration consolidation.

Required proof for this consolidation is bounded: same exact approved target through old public entrypoint → canonical admission → existing API or SRP adapter; no send before Undo; one send under duplicate delivery/crash; uncertain result forbids fallback/resend; same/late/conflicting capture replay; cross-tenant/source/team refusal; native ACK plus unconfirmed session retained; preserved imported IDs/queue receipts; old drain cannot take a migrated obligation; only one verification cycle; whole native-write callsite census includes package methods. It does not require rebuilding a browser lifecycle first.

## Limits and preserved work

- This audit inspected source and git snapshots, not live credentials, production counts, Apple traffic, or deployed replica versions. “Active” means wired reachable production code, not measured call frequency.
- The baseline already contains the SRP stack and individual-key setup. No documentation-only assumption that headless means Chromium is used here.
- No Actions schema exists on the inspected main baseline; feature Actions data is unactivated local/preview state. Actual legacy drafts, pending actions and recorded receipts still require conservation. Do not create an operator migration program for hypothetical deployed feature records.
- No implementation files, DDL, manifests, git index, or frozen checkpoint were changed by this audit.
