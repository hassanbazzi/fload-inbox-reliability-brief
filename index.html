The provider owns the remote reality.

All storage remains in one PostgreSQL database. The current four namespaces express contract ownership; retaining them is a design choice, not a requirement of normalization. Provider boundaries remain explicit whichever layout wins.

One protocol, distinct work.

Generation permission does not authorize publication. Provider acknowledgement does not prove live content. Every flow keeps those distinctions visible.

Who approved, edited, retried or assigned this?

action_command records principal, actual actor, channel, delegation, request digest and outcome. action_command_target records expected and before/after state for each affected ticket. Approval points back to that command and forward to the exact authorized revision.

History combines commands, revisions, approvals and attempts. It does not require another generic event table. Agent policy approval names the exact policy revision and agent run. An unlinked Slack/Discord identity cannot borrow the installer’s approval authority.

Crash and retry

SQL survives transport loss

A worker-owned recovery sweep finds due obligations. Enqueueing does not consume them. Schedule generation helps distinguish obsolete deliveries. Same-ID delayed jobs still need explicit promotion; duplicate add alone does not repair them.

External uncertainty

A lease cannot cancel a provider request

After timeout or confirmation failure, retain uncertainty and resource exclusion. Read the exact remote target. Retry only when evidence or provider idempotency makes it safe.

Known prototype regression: the HTTP handler commits approval but still waits for the enqueue promise before responding. A stalled Redis request can delay acceptance. This is reproduced and remains an explicit implementation fix.

Historical prototype: why 25 → 31 tables? Two provider listing contracts + one ASC upload-step contract + three native receipt tables = six additional relations. Moving Apple Ads content into its namespace adds zero. The split reduces provider fields in common rows but costs joins and cross-table constraints.

Separate factsReason they cannot safely share one mutable row
Ticket / revisionOne stable work identity, many immutable versions.
Approval / executionImmutable permission versus changing delivery progress.
Step / attemptOne intended effect, several calls and observations.
Parent link / membershipPermanent structure versus the exact set reviewed at a point in time.
Shared work / personal readOne organization decision, different attention per member.
Notes / terms / countries / mediaRepeating facts with explicit keys and closed roles; no array or JSON escape hatch.
Where we deliberately use fewer tables
  • One ordinary ticket type for both parent and child.
  • One revision envelope for proposals, baselines and observations.
  • One constrained Apple Ads content table for seven current operations.
  • One constrained advisory relation for supported advisory variants.
  • No universal event store; history reads existing immutable facts.
  • No generic SQL job table or provider-specific approval subsystem.

Provider one-to-one extensions are a deliberate ownership choice, not a normalization theorem. Receipt and listing-contract consolidation need concrete constraint-preserving alternatives. V8 consolidates the three provider receipt tables into one constrained Actions receipt and moves the Play listing contract into typed listing content, reducing the Actions surface from 31 to 28 relations. It adds two Usage relations and modifies the existing usage log. The explorer retains the old 31-table prototype for comparison.
