Architecture review · 8 September 2026

A smaller model. An explicit schema change.

Decision

One Actions boundary.
Fully relational facts.

Permanent tickets, typed immutable revisions, exact approvals, durable jobs, personal read receipts.

4 new tables + 2 evolved tablesSix-table candidate · strict relational fields · not yet implemented
Fourteen-table proposal withdrawn

The extra splits were not justified

Evolve pending_action and inbox_item_state. Add revisions, relationships, history and jobs.

One revision table uses explicit columns and closed variant constraints. Provider evidence lives in typed history. No separate content/observation table for each domain.

Blocking gaps corrected in the plan

What changed after review

Strict types

No JSON/JSONB, serialized payloads, arbitrary key/value fields, open metadata or catch-all variants. Closed contracts from database to UI.

Resource conflicts

Two tickets targeting the same review or listing also serialize at dispatch. Ticket locks alone are insufficient.

Uncertain writes

Reconcile the earlier write before editing or approving replacement content. Preserve late provider evidence.

Partial approval

One root command plus an approval event for every selected child. All commit together, with exact revision and membership references.

Generation

Generated content needs its own human or explicit policy authorization. Approving generation cannot approve unseen copy.

Migration

Real migration replay, final writer handoff, then removal of old authorities. No indefinite dual model.

Review status: the fourteen-table design is withdrawn. This smaller candidate needs a field-complete schema, migration fixtures and concurrency proofs. Table count alone is not architecture validation.
