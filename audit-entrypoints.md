## Current design boundary — latest user direction

The active design covers the 18 currently supported executors plus actual current generation, iteration, prerequisite, package and informational workflows. Retired ads/product vocabulary below is migration awareness only: **do not add it to the new runtime schema, content families, command types or dispatcher.** Preserve existing receipt/link evidence at the migration boundary without making the working design carry old behavior.

## 1. What the end-to-end boundary must encompass

The inbox currently composes five wire source families from three live row loaders. The broader Actions manifest has 61 entries, including 18 registered executors; production contains additional historical action keys absent from that manifest. A migration scoped only to the visible inbox cards or to 18 executor keys would omit real records and alternate mutation paths.

The proposed ownership rule is: **Actions owns the ticket, immutable proposal, authorization decision, organization workflow, and intended effect. Agents owns agent computation and scheduling preference; provider domains own their transport and authoritative observations.** A source system can retain its own domain row, but cannot retain a second independently writable approval/status for the same ticket. Read state belongs only to a member. Assignment, reason owner (`customer`/`Fload`), creator, approver, and execution actor are different facts.

### Source families

| Current wire family | Current identity and state | Final object and conversion |
|---|---|---|
| `pending_action` | Real ID; raw status text, mutable params/before/after; required orchestrator run even for synthetic producers | Same permanent action ID where valid; current proposal becomes immutable revision. Migrate approval evidence honestly. Remove run-as-parent requirement. |
| `agent_request` | Real ID; organization+idempotency key; mutable request payload plus events; request approval and dispatch separate | Ordinary ticket for generation, investigation, prerequisite, or information. Keep typed Agent request/run domain correlation, with only one authority for the human workflow. |

## 4. Required end-to-end flows

### A. Human approves one public write

1. UI/API/MCP/chat reads ticket ID, revision ID, organization workflow version, exact visible content and current permissions.
2. `ApproveRevision` carries command idempotency key plus expected versions. Server resolves actor from canonical authorization; no body-supplied actor.
3. One transaction checks scope/eligibility/current revision, stores decision and selected content, execution obligation, shared history and server Undo deadline. Response says accepted only after commit.
4. Due execution is signaled to BullMQ. Delivery claims the durable execution/step generation before transport access; duplicate deliveries are harmless.
5. Provider write uses the approved content. Attempt is durable before I/O. Known no-write rejection, acknowledgement and uncertainty are distinct outcomes.
6. Readback records the exact observed surface/version. Editable ASC state, live state and measurement are separate evidence. Parent/detail/history links survive every result.

### B. Batch decision and handoff

Read a permanent parent + membership revision containing child IDs and child revision IDs. Submit selected member revision IDs; never send just an asset ID or query predicate. Lock parent and selected children in stable order. Either record the complete approval selection atomically or return a conflict with no partial decision. Execution may settle each child independently. A newly arriving review/locale becomes new work or an explicit unapproved membership revision; it cannot join the approved snapshot. Retry only unresolved members, after readback where uncertain. An empty/partially completed batch remains a permanent ticket.

### C. Revise against approve

`Revise`/`StartIteration` requires expected current revision and workflow version. Approval and iteration share the same write/claim boundary. A worker may compute outside the transaction but commits only if the generation claim remains current. “Add locale” changes package membership revision. Human edits and dismissed fields are included in the next immutable revision and invalidate stale approval. Editing published review content creates a new proposed effect; it cannot reset the former attempt row for reuse.

### D. Undo, cancel and compensation

`UndoApproval` references the accepted decision, uses the database deadline, and succeeds only before any selected member's write claim. Batch Undo is atomic while all selected members remain cancellable. Once a member crossed the external-effect boundary, return explicit `too_late` with current child states; no claim that Undo restored provider content. Optional cancellation of still-unstarted children is a separate explicit command. A later revert is a new approval of an exact reverse proposal, linked to the original execution and baseline.

### E. Provider or user handles it externally

Readback or synchronization observes the expected condition already true, or observes a reply written externally. Add observation + `resolved_externally` outcome and retain prior proposal/history. If the provider resource disappeared, preserve ticket and evidence with an explicit terminal/blocker disposition. Do not delete the review/ticket graph to make the inbox quiet.

### F. Advisory and prerequisite

`Acknowledge` records a shared disposition, never execution/published evidence. `Snooze` belongs to the organization and has a server due time. Prerequisite resolution is a typed observation; dependent execution becomes eligible only for the existing approved revision and existing authorization scope. Changes requiring different content/scope return for approval.

### G. Autonomous work

Agent/system generation supplies a stable producer identity + source occurrence key. Exact automation policy version and bounded authorized scope substitute for a human approval only where policy actually authorizes the effect. “Agent mode” is not a universal authorization. New child proposals outside that scope stay awaiting review. Historic null approvers remain explicitly unknown, not system-approved by migration inference.

### H. Repairs and erasure

Recovery uses the same command/claim transitions; operational scripts must no longer mutate lifecycle/content directly. Admin reset cannot cascade-delete permanent work by removing a synthetic run. Account/organization erasure remains a distinct audited retention operation; durability is not a promise to retain data against legitimate deletion requirements. Tests/fixtures use guarded isolated databases and typed fixture construction.

## 5. Command and actor contract

Command names below are semantic names for the final contract, not an additional queue or dynamic command registry. Each is a closed discriminated schema; final SQL/API names may align with the consolidated specification.

| Command | Required pinned input | Authority and concurrency | Durable outcome |
|---|---|---|---|
| `CreateTicket` / `CreatePackage` | producer occurrence key; typed target/content; explicit child IDs | Scoped producer; uniqueness on occurrence+purpose; equal replay returns same identity | Ticket, first revision, source links, event; children/membership atomic |
| `Revise` / `StartIteration` | action ID; expected version/revision; exact edit or instruction | Eligible state; conflicts with approval using same lock/CAS | New immutable revision or durable generation obligation; explicit discarded output |
| `ApproveRevision` / `ApproveSelection` | action/package revision; selected child revisions; idempotency key | Current authorization; no stale/missing revision accepted | Approval actor+scope, exact pins, execution obligation, deadline, event |
| `UndoApproval` | approval ID; expected state; command key | Database time before deadline; no effect claim | Decision revoked with history, execution cancelled; exact conflict otherwise |
| `RejectRevision` | current revision; reason; command key | Shared human workflow; no false rejection of already-written effect | Rejection snapshot/history, terminal disposition |
| `Acknowledge` | information revision; command key | Advisory/prerequisite semantics; never provider execution | Shared resolution and actor |
| `Snooze` / `Resume` | expected state/version; requested due time | Server normalizes deadline; superseded observations cannot reactivate completed work | Shared due time and event |
| `Archive` / `RestoreVisibility` | ticket ID/version | Presentation retention only; no content/execution rewriting | Shared archival fact and event, stable detail URL |
| `MarkRead` / `MarkUnread` | ticket ID; user's observed revision/event sequence | Personal principal only; no workflow lock/version increment | Per-user read watermark, no workflow changes |

| `AssignOwner` | ticket ID/version; scoped member/team | Organization workflow permission | Assignment event; separate from approver, creator and blocker responsibility |

Every mutating command uses a tenant-scoped idempotency key, persisted canonical request fingerprint and typed result. Same key + same request returns the original result; same key + changed revision/selection/text returns idempotency conflict. Store typed result columns/relations rather than an open result blob. A lost client response is solved by querying/replaying the same accepted command, not generating a fresh UUID and hoping dedupe succeeds.

Actor records must distinguish: member session, API credential+owner, delegated OAuth user, externally authenticated Slack user/team, externally authenticated Discord user/guild, agent run, system recovery worker, and admin impersonation (real actor plus acting-for member/org). Historical absent/unresolved actor is explicitly historical/unresolved; do not create a fake identity. New external approve buttons require a real mapped member with current authorization, or a specifically configured bounded external-approval policy; default new unmapped users to a sign-in/deep-link flow. Keep external interaction ID for replay prevention and exact action+revision in the signed/validated button reference.

Authorization continues through `authorize(authorizationPolicy.*)` as the first direct preHandler. Current inbox routes use organization session; public action routes use `read:agents`/`write:agents`; provider work routes use `write:reviews`, `write:aso`, or ASA write scope; catalog/backlog use admin or impersonator. Command authorization must preserve the caller's capability-specific scope. Routing an ASA request through generic Actions must not grant an unrelated `write:agents` credential an implicit larger capability. Membership/credential revocation before provider dispatch must be checked according to the explicitly stored authorization policy, without changing approved content. [Canonical authorization](https://github.com/fload-ai/fload-platform/blob/63275b2f51ac5b5a151a9a6683c813423e682785/apps/api/src/plugins/auth.ts#L273).

## 6. List/count semantics to implement

Current behavior: list chooses up to 200 rows **per source**, filters/derives batches, sorts, then slices the combined set; counts choose 500 per source. List's default terminal window is 14 days, optionally up to one year; counts always use default. Pending actions preserve pending/blocked/failed regardless of age and use update time for other states, plus experiment exceptions; requests use creation time for nonattention states. Requests filter asset strictly; actions include organization-level items in every selected app. Review drafts omit sent/claimed rows and reviews older than 90 days. These are explicit disagreements despite shared bucket derivation. [List](https://github.com/fload-ai/fload-platform/blob/63275b2f51ac5b5a151a9a6683c813423e682785/apps/api/src/services/inbox.service.ts#L607), [count](https://github.com/fload-ai/fload-platform/blob/63275b2f51ac5b5a151a9a6683c813423e682785/apps/api/src/services/inbox.service.ts#L985), [request scope](https://github.com/fload-ai/fload-platform/blob/63275b2f51ac5b5a151a9a6683c813423e682785/apps/api/src/services/inbox.service.ts#L1110), [action scope](https://github.com/fload-ai/fload-platform/blob/63275b2f51ac5b5a151a9a6683c813423e682785/apps/api/src/services/inbox.service.ts#L1213).

The canonical read model should define one SQL relation and one filter contract: organization, explicit app scope (`all`, `app_only`, `app_plus_organization`), actor visibility, view/bucket, include-archived, terminal horizon, parent/child presentation, unread filter, query/sort version. Count that relation before pagination; fetch it with stable keyset cursor and deterministic tie-breaker `action_id`. Return `items`, `next_cursor`, exact `total_matching`, exact bucket/view counts, unread count and `as_of` from the same database snapshot. Never sum parent and children into a count of cards while rendering only the parent. Return a separate count of leaf work units when product wants progress.

Sibling pages live in changing data. Cursor carries filter/sort fingerprint and the traversal boundary; the response is explicit that counts are exact for its snapshot, not a perpetual cross-page snapshot. Initial list and counts must be one snapshot; a separate badge/count endpoint shares the same filters and predicate. Realtime notifications invalidate/refetch or carry ordered durable event sequence; dropped events cannot change authority. All historical detail/history/children endpoints paginate. An expired candidate window cannot erase an accepted ticket; hide/archive placement is an explicit filter, stable detail remains.

Expected invariants: sum(bucket counts)=sum(view counts)=total matching cards; each card occurs once; page union reaches every qualifying card, including oldest work; arbitrary row caps never enter business visibility; unknown lifecycle value cannot map to approved; entitlement/asset deletion changes show explicit restrictions on retained obligations rather than silently dropping them.

## 7. Strict historical migration classification

The private census was used to enumerate actual observed keys and field names, not copy customer content. An observed key's current state is not enough to infer whether a store write happened. Only linked receipts and observations can prove that. An old `executed` or `completed` label becomes historical reported outcome when evidence is absent.

The manifest and observed-key maps below are finite. Retired content belongs only to migration accounting and existing receipt/link preservation; it is not a new runtime subtype or a second lifecycle. For payload keys outside the enumerated mapping, stop/quarantine the migration row for explicit classification; do not put arbitrary JSON, an EAV map, or serialized JSON text into the final schema to bypass strict typing. A production shape census of nested arrays/objects and value types is required before declaring content migration total; the available aggregate top-level key census does not establish those nested types.

## 14. Required proof and remaining data gate

- Maintain a manifest classification test covering all 61 catalog entries and an active-schema exhaustiveness test for all 18 executable definitions plus current derivations. Keep retired stored variants only in migration accounting; no new runtime types for them. Adding a key must fail compilation/schema inventory until kind/content/owner/authorization/transition/evidence/migration/query semantics are specified.
- Every row in the HTTP map that can write ticket work must pass the same command idempotency/stale-revision suite. Assert old compatibility adapters reject missing revision; never auto-approve the server's newer revision on an old client's behalf.
- Concurrency: approval versus iteration/edit/member changes; competing approvers; batch member revision changes; Undo versus claim at the exact deadline; permission revocation; late worker/late readback; concurrent manual provider edits; duplicate producer and report delivery.
- Retry/crash: transaction committed but response lost; API dies after webhook transport ACK; DB commits before queue enqueue; queue succeeds before dispatch bookkeeping; duplicate queue delivery; crash before/after each provider step; provider write succeeds before receipt; stale claim response after another worker settled; queue retention expiry and recovery scan.
- Derivation: every requested locale/review yields one persistent child outcome; zero generated results cannot become completed generation; adding work changes only an unapproved new membership revision; report version/source fingerprint remains fixed; manually edited/dismissed fields survive regeneration; media versions remain immutable.
- Query: more than every old cap, old actionable work, equal sorting timestamps, shared vs personal state, parent card vs leaf count, org-only work under each app filter, horizon, feature/asset visibility changes, archived detail, pagination cursor mismatch and count/list same snapshot.
- Migration: synthetic batch alias ambiguity must be visible, not guessed. Per-row exact content/revision/receipt/actor/source links reconciled; no replacement of absent approved content by current draft. Validate all observed retired subtype fields, nested collection cardinalities, missing identities and out-of-domain statuses before cutover. Unknown fields/statuses fail closed, never map to approved or enter an open payload column.
- Repository safety: use the prescribed worktree; Drizzle generate→migrate, never db:push; isolated test DB from test setup, never singleton database import; tests reproduce defects before fix; run unit/integration/typecheck/lint and required Semaphore checks. No production provider writes/deployment in this work.

This audit has not reproduced the race windows at runtime or run migration tests. It closes the code and observed-key inventory, and gives a finite endpoint/writer denominator. The top-level aggregate census does not prove a complete nested-content decoder; that decoder and per-row conversion validation remain required before the normalized DDL/cutover can be called implementation-ready. The final architecture must not conceal this gate with a generic `legacy_payload` or JSON-as-text field.
