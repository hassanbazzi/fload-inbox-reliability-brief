# FLO-1355 runtime reuse audit

Read-only source audit, 2026-09-21. No implementation, migration, test, database, provider, or runtime changes were made for this audit.

Compared `origin/main` **b5253b2d799cf35863a9d0c31e3481762e44afde** with HEAD **d0945bb3ca61370e3d783d4fcec9573f58d66e01**, then inspected the separately preserved uncommitted lifetime20 overlay. Paths and line numbers below refer to the working tree at audit time; other agents have unrelated uncommitted work. Labels are recommendations, not deletion instructions or activation approval.

## Immediate conclusion

**Do not ship the uncommitted common account-lifetime rollout.** It contains a source-level headless integration defect and changes existing job concurrency substantially without a worker deferral implementation. Preserve its archive and useful native-result/deadline tests. Reuse the existing headless SRP/session owner before deciding that private review capture needs Chromium or all-account serialization.

The committed Actions worker/recovery modules are **unregistered factories**, not a second running worker deployment. The branch has not replaced the existing queue, process lifecycle, work-execution kernel, outboxes, or entitlement implementation. However, it added substantial domain execution/recovery code alongside them. Some added semantics are missing from the older implementation; that does not justify rebuilding its scheduling, authentication, billing, or session infrastructure.

## What actually serves reviews today

The current production path is not browser-only. `services/worker/scraping/helpers/reply-helpers.ts:340–387` resolves a data-source connector and creates an official API client when `selectTransport(creds) === 'api'` with an individual key. `sendReplyPreferApi` at line456 chooses `sendReplyGuarded` or `updateReplyGuarded` at line496, retains the API resource mapping, and only falls back to `scraper.respondToReview` at line567 when that path permits it. `sendReplyIOS:574` subsequently refreshes through `scraper.getReview`.

The normal scraper prefers the existing headless SRP manager: `packages/apple/src/app-store-connect-web/client.ts:1125` obtains it; `ensureWebSessionProvider:1207` resolves/switches the native team; `hydrateBrowserFromWebSession:1267` copies cookies to the existing page; `ensureLoggedIn:1605` tries that path before browser login. The existing review methods issue HTTP using cookies, not DOM-driven reply submission (`getReview:6728`, `respondToReview:6848`). Thus existing flows still have a browser/page shell, but they already use headless authentication and direct HTTP. The new private owner unnecessarily bypassed that authentication path before testing reuse.

The existing API fallback has weaker mapping/failure semantics than the new exact Actions contract. Its presence does not prove the old mapping or fallback is safe for a new uncertain-write protocol. Conversely, that contract difference does not justify discarding working individual-key transport or rebuilding session acquisition. Parent is separately auditing the native identity/transport choice; this report does not certify an API cross-ID mapping.

## Concrete headless integration defect in uncommitted20

`packages/apple/src/app-store-connect-web/web-session.ts:229` defines `accountCacheKey(email)` as SHA256 of the lowercase email. `getSession:247,297` supplies that **hashed account key** to `SessionStore.get`; `refreshSession:241` supplies it to `clear`; login uses the same key for store and lock operations.

The modified `apps/api/src/connectors/app-store-connect/web-session/web-session-io.ts:192–237` defines `exact(account)` as `account !== ownership.email` and calls it from every store operation and lock acquisition. `ownership.email` is the original email. Normal manager calls therefore throw `ASC account lifetime mismatch` before cache use or SRP login. The client catches headless failures and falls back to browser login (`client.ts:1125` onward), so some jobs may still complete while the intended headless path is disabled. Direct manager callers reject.

This is a deterministic source-level mismatch, **not a newly executed regression test or observed production incident**. The frozen20 compatibility test at `provider-package-compatibility.test.ts:95–104` extracts private `deps.makeTransport` and tests its timeout directly; it never calls `manager.getSession` and therefore misses the real contract. Prior green test counts do not establish this integration is safe. No fix or new test was made during this audit.

## Smallest supported headless reuse boundary

The existing dependency seams support a private composition: use `WebSessionManager` with a private in-memory/no-shared-writeback `SessionStore`, its existing SRP/2FA/transport dependencies, and one explicitly selected native team. The manager creates a separate CookieJar; no new auth engine is needed. It may also reuse that private jar during a bounded session instead of logging in per review.

This is a supported **source-level integration option**, not finished or provider-tested code. Required adaptation remains explicit:

- Preserve raw `AppleHttpResponse.text` for the lossless decoder; its parsed `json` may already round a large numeric ID.
- Add or adapt request cancellation/deadlines. Existing `AppleHttpRequestOptions`/`WebSession.request` lack an AbortSignal parameter. The one-shot transport also checks response URL, which the existing Apple response abstraction does not expose. Do not invent successful URL/correlation facts to satisfy it.
- Observe the native session principal/team. `WebSession.currentUserEmail:87` returns configured account data; it is not native identity evidence. `switchProvider` HTTP success alone also cannot replace an observed exact principal.
- Separate private session reuse from shared cookie cache reuse. A cloned jar from shared cached cookies may represent the same server session; local object separation does not prove provider isolation.
- Test the real manager→store→transport path and context change before/after an operation. Preserve a native ACK or unknown result when local cleanup/ownership fails; never turn an already sent request into `not_sent`.

## Throughput and existing callsites

Existing `queue.ts:1674–1681` groups jobs by `email:developerId:lane` where available, otherwise `email:lane`; `worker.ts:1151` permits15 per group. Browser slots separately default to15/account (`config/scraping.ts:15`, `browser-concurrency.ts:35`), wait/poll for availability, and are acquired by `worker/scraping/browser-initialization.ts:127`. These are capacity controls, not proof that team mutation is safe.

The new lifetime key is one SHA256 of **trimmed/lowercased email**, shared across provider, lane and transport (`asc-browser-account-lifetime.ts:113`). Exact principal bytes remain unchanged. Acquisition is non-waiting SET NX and returns `busy`. Legacy lifetime may last30min; private lifetime10min/50 sequential operations; Redis TTL180s renews every30s, with30s reserve; HTTP/launch budget60s and result/cleanup grace30s. This reduces intended simultaneous account work from up to15 browser slots to **one lifetime**, potentially including many operations and user/2FA waits. It is not throughput-neutral, nor does it imply a measured15× throughput change.

Scraping jobs default to **one attempt** (`queue.ts:367`). The new typed `AscBrowserOwnershipError('busy')` has no installed BullMQ delay/defer handling. Contending sync/onboarding/review jobs can fail instead of waiting under the existing browser-slot policy. A retry loop or bypass is not a safe audit-time fix.

The common wrapper affects these ten existing constructor sites and the new private owner: `routes/assets/reviews.ts:395`; `services/review-sync.service.ts:285`; `services/aso/asc-promo-text-writer.ts:177,430,765`; `services/aso/asc-listing-fetch-scraper.ts:63,444`; `services/aso/check-applied-experiments.ts:166`; `connectors/app-store-connect/fetch-asset-price-catalog-via-scraper.ts:57`; `services/worker/scraping/browser-initialization.ts:154`; and `services/actions/providers/app-store-connect/review-browser-session.ts:140` is the new site (ten preexisting constructor sites plus this eleventh total). These callsites include direct routes/services outside the queue, so queue-group changes alone would not supply complete lifetime coordination.

## Existing durability: reuse without overstating equivalence

Existing review draft work already persists intent and claims: `reply-helpers.ts:140` and `claimQueuedDraftForSend:213` update `pendingSendAt` before sends; `services/reviews/queue-approved-reply.ts` and `reply-readback-scheduling.ts` persist queue/readback booking state. `services/inbox-work/execution-receipt.ts:24` verifies definition-owned execution/queue acknowledgements. `work-execution/applied-verification.ts:167,374,913` supplies existing delayed review readback and queue dispatch.

These are real capabilities that should have been inventoried before creating a new recovery composition. But the process-local grant is not a durable native-attempt claim, and `execution-log.ts:15–18,30` intentionally treats persistence as best-effort after work. Its readback anchor resolves the newest org/capability/work record (`:70–82`), not the new exact original/late attempt correspondence. Likewise the managed-alert outbox explicitly permits crash recovery to **resend** (`:12–16`). It is unsuitable as authority to resend a possibly applied review mutation. Keep the required stronger effect semantics; reuse existing surrounding infrastructure rather than asserting either complete equivalence or complete absence of prior durability.

## Missed capability scans and audit limits

The source evidence identifies concrete scans that should have preceded scope expansion: production API-first send/read routing; SRP manager dependency contracts and raw-text transport; existing draft claims/readback booking and work-execution receipts; current outbox/lifecycle/singleton scheduling; and every legacy scraper acquisition plus queue attempts/capacity. The lifetime tests then bypassed the manager boundary they needed to validate. These omissions explain avoidable implementation work without assuming that all new domain guarantees were already available.

No HEAD-vs-main implementation changes were found in `queue.ts`, `worker.ts`, `index.ts`, `lifecycle/`, `services/work-execution/`, `entitlements.service.ts`, `singleton-lease.ts`, the inspected outbox service, `web-session.ts`, or `undici-transport.ts`. New Actions execution factories remain unregistered; the uncommitted common scraper wrapper would affect active production paths if shipped. This distinction matters more than the total added file count.

This bounded audit did **not** run tests, connect to Apple/Redis/Postgres, establish Apple server-session isolation, benchmark capacity, certify current credential availability, or audit all billing/RLS/identity/policy branches. Client-channel and deletion outboxes were inventoried by registration, not fully audited. It does not recommend abandoning exact capture/finality guarantees or claiming current work-execution already provides them.
