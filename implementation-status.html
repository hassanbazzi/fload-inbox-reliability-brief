What happens to a piece of work

  1. 1 · ProposeCreate one ticket and seal the exact content. New copy becomes a new revision.
  2. 2 · ApproveRecord the actor, revision and Undo deadline in one server transaction.
  3. 3 · DeliverPersist the attempt before a provider call. SQL retains work if a worker or queue fails.
  4. 4 · VerifyKeep acknowledgement, published content and an uncertain request distinct.

Shared work, personal reads

Approval, ownership, holds and outcomes belong to the organization. Marking something read changes only that person’s watermark.

A batch is still a ticket

Membership pins permanent child tickets and their revisions. New reviews cannot silently join an approved batch. Progress is derived from its children.

One owner for each fact

Actions owns workflow. Domain schemas own content. Provider schemas own native identities and receipts. Composition selects the immutable contract.

Queues only wake workers

There is no replacement generic jobs table. Execution records represent accepted obligations and attempts; existing queues transport wake-ups.

Every view has an explicit continuation

Root tickets, individual children, archived work, pinned batch membership and ticket history use bounded pages. Counts come from the same eligible relation and database snapshot as the page.

Stable position

Ticket and history cursors retain database microseconds and a deterministic ID tie-breaker. Archiving the cursor row does not break continuation.

No silent limit

At most 100 items per response, with a next cursor. This is a page size, not a cap on accessible work. Recovery scans filter worker compatibility before their limits.

A later request sees newer committed data. New items ahead of a cursor appear on refresh; changing filters requires a new traversal. Passive provider waits do not consume the five client-attention slots.

Built now, and still to build

Implemented and locally tested

  • Permanent identity, exact command/history and immutable revisions.
  • Personal read compare-and-swap, atomic approvals and server Undo deadlines.
  • Review/advisory content, execution storage, recovery cycles and SQL discovery; typed read API and SDK remain inactive.
  • Pinned membership, current-child workflow, archived access and matching counts; SQL/HTTP/SDK tests traverse packages larger than 100 items.
  • Single-request Apple review ports, strict native decoding and atomic original, late and conflicting write receipts, with exact history.

Required before cutover

  • Complete trusted source binding, prewrite admission, dispatch, readback, effective finality and resource release.
  • ASO/localizations, requests, generation/usage and every remaining producer.
  • Historical conservation/import, outstanding-work handoff, erasure and old-writer removal.
  • Batch ownership transfer, route/UI activation, complete end-to-end and load checks, and CI for the full overhaul. The separate provider-hardening PR has passed CI.

Existing platform paths remain authoritative. Importing the new modules does not start workers or send provider requests.
