# FLO-1355 — dispatch, provider steps, recovery, and data readiness

Investigated 15 September 2026 against `fload-ai/fload-platform` commit `63275b2f51ac5b5a151a9a6683c813423e682785`. This is a source and architecture audit, not an implementation or production deployment. The canonical candidate is `schema-core.sql` plus the content, revision, command, and execution guard SQL files. This audit explains their evidence and boundaries; it is not a migration. Existing behavior, proposed decisions, and unverified provider assumptions are distinguished explicitly. No customer content, account IDs, live queue payloads, credentials, or private census records appear here.

## Decisions needed in the final architecture

1. **A durable execution is an approved intent, a step is a specific effect, and an attempt is one physical interaction.** Existing operations already contain several effects. One job row cannot honestly describe them all.
2. **BullMQ remains transport and capacity control.** Postgres owns eligibility, exact approval, next due time, uncertainty, and retained evidence. No generic SQL queue is added.
3. **Persist the planned effect before crossing the provider boundary.** Persist a separate attempt before each request that can mutate provider state. Grouping several requests in one wrapper does not make them atomic.
4. **One retry policy controls each effect.** Remove automatic mutation retries from lower clients as well as queue workers; retain safe read retries. An outer worker cannot enforce this rule while a client internally resends POST requests.
5. **API/browser fallback is an attempt transition.** A definite failure before writing may select another transport. An ambiguous response first requires reconciliation.
6. **Freeze dependencies and copied content before approval.** Primary-locale fallback text, App Clip images, unrelated Play listing fields preserved by a PUT, and review update mode must be attributable and versioned. They cannot be augmented invisibly after approval.
7. **Shared lifecycle progress is derived from durable child outcomes.** Completing generation creates drafts; sending a provider request yields acknowledgement; observing the exact saved content yields confirmation; observing it publicly yields live evidence; experiment measurement is a later domain fact.

## Findings that deepen or change the previous review

### D1. ASC review replacement need not be assumed to require deletion

The current client implements review replacement as DELETE followed by POST. The wrapper retries POST once when deletion succeeded and creation threw, then returns `responseGone`. This has a real process-crash boundary between removal and replacement, plus an ambiguous-POST retry boundary. [Transport](https://github.com/fload-ai/fload-platform/blob/63275b2f51ac5b5a151a9a6683c813423e682785/apps/api/src/connectors/app-store-connect/review-reply-transport.ts#L106), [client](https://github.com/fload-ai/fload-platform/blob/63275b2f51ac5b5a151a9a6683c813423e682785/packages/apple/src/app-store-connect-api/client.ts#L490).

**Current official Apple documentation contradicts the code comment that replacement requires deletion.** Apple documents the same response POST endpoint for creation and replacement and allows at most one response per review. The final adapter should prefer the documented non-destructive replacement after contract validation. This audit did not mutate an Apple review to test that behavior. Preserve old delete/create evidence in the bounded migration archive and resolve interrupted old operations before retiring the old writer; the active planner contains only the documented upsert step. [Apple response resource](https://developer.apple.com/documentation/appstoreconnectapi/customer-review-responses?changes=__9_1), [create or update endpoint](https://developer.apple.com/documentation/appstoreconnectapi/post-v1-customerreviewresponses).

### D2. Play write retries exist below the apparent safety boundary

`sendReviewReply` explicitly avoids switching from the cached session to browser after timeout/5xx, which is useful. However, both `playConsoleRequest` and `browserFetchWithRetry` retry 500/502/503/504/network failures for all methods, including POST, and callers pass three attempts. Listing writes use `fallbackOnAuthError:true`; after a thrown session error exhausts retries that flag also selects browser fallback, even though the error was not necessarily authentication. These are source-confirmed control-flow gaps, not a claim that a duplicate write was observed. [Session retry helper](https://github.com/fload-ai/fload-platform/blob/63275b2f51ac5b5a151a9a6683c813423e682785/packages/google/src/play-console-web/client.ts#L835), [browser retry helper](https://github.com/fload-ai/fload-platform/blob/63275b2f51ac5b5a151a9a6683c813423e682785/packages/google/src/play-console-web/client.ts#L966), [review caller](https://github.com/fload-ai/fload-platform/blob/63275b2f51ac5b5a151a9a6683c813423e682785/packages/google/src/play-console-web/client.ts#L8174).

**Change:** split read transport and mutation transport contracts. Mutations issue exactly one network request per persisted attempt except a specifically documented, known-not-applied authentication retry, which must itself remain observable. Never infer retry safety from the HTTP verb alone: absolute PUT may overwrite a teammate's newer value.

### D3. Google Play edit ownership is app-wide and commit policy matters

The existing metadata writer performs edit-create → current-listing GET → listing PUT → commit POST and only returns the edit ID after completion. All three mutation calls sit inside one guarded wrapper. The three single-field writers independently repeat the edit transaction. [Current metadata flow](https://github.com/fload-ai/fload-platform/blob/63275b2f51ac5b5a151a9a6683c813423e682785/packages/google/src/play-console-web/client.ts#L8342), [wrappers](https://github.com/fload-ai/fload-platform/blob/63275b2f51ac5b5a151a9a6683c813423e682785/apps/api/src/services/work-execution/guarded-gplay-listing.ts#L24).

Google documents that creating another edit invalidates the user's previous edit, and an app commit or console change invalidates other edits for that app. Changes may take hours to propagate. Therefore serialize by canonical Play app, not merely locale or connector. Persist the returned edit ID before doing its next step. A missing/expired edit after an ambiguous commit does not prove the commit failed. [Google edit workflow](https://developers.google.com/android-publisher/edits).

Google's commit endpoint also documents a default that can cancel existing changes in review. **Make `changes_in_review_behavior` a closed approved field and use `ERROR_IF_IN_REVIEW` by default.** Broader cancellation requires an explicit authorization that the user can review. The current caller omits that query option. Verify its behavior with the credential/session transport used by Fload before rollout. [Google commit contract](https://developers.google.com/android-publisher/api-ref/rest/v3/edits/commit).

### D4. One App Clip image wrapper contains N+2 writes

App Clip creation is currently a tail of `create_locale`. A card is created, an image reservation is created, N upload operations transfer byte ranges, and commit marks the image uploaded. Existing repair can delete an incomplete reservation. These have separate outcomes and resource identities. The wrapper currently treats reserve/upload/commit as one write. [Guarded App Clip contract](https://github.com/fload-ai/fload-platform/blob/63275b2f51ac5b5a151a9a6683c813423e682785/apps/api/src/services/work-execution/guarded-app-clip.ts#L17), [actual upload sequence](https://github.com/fload-ai/fload-platform/blob/63275b2f51ac5b5a151a9a6683c813423e682785/apps/api/src/connectors/app-store-connect/app-clip-write-transport.ts#L105).

**Change:** preserve the reservation ID, immutable media digest, byte range, and per-chunk result. A lost reservation response requires inspection; a new reservation is not a generic retry. No durable upload credentials in the inbox schema: reacquire short-lived upload authorization from the provider using the resource identity. If that is impossible, retain an explicit blocked outcome. Copying the current primary card at dispatch violates exact-content approval; pin the copy source and version at proposal time.

### D5. ASA aggregation hides more than one provider request

The platform executor resolves all currencies/resources before writing and has useful duplicate-create guards. Bid updates are grouped by campaign/ad group; the lower client then chunks each group at 1,000 updates. A successful earlier group/chunk plus a failed or ambiguous later group is partial execution. The current catch describes the remaining groups as not applied, which cannot be assumed for the failing request if its response was lost. The lower bulk mutation helper checks HTTP success but does not return per-item receipts. [Executor](https://github.com/fload-ai/fload-platform/blob/63275b2f51ac5b5a151a9a6683c813423e682785/apps/api/src/services/work-execution/platform-executor.ts#L490), [client chunks](https://github.com/fload-ai/fload-platform/blob/63275b2f51ac5b5a151a9a6683c813423e682785/packages/apple/src/apple-ads-api/keywords.ts#L144).

**Initial simplification:** each approved keyword change is a child execution with a single target. Use the existing bulk endpoint with one item initially. Session reuse is fine. Reintroduce request batching only with an explicit request-to-step mapping and per-target result/readback; never hide a multi-target request inside a supposedly single-target attempt. Keep exact currency checks and case/trim/match-type keyword identity. A duplicate term found during reconciliation is evidence of matching state, not proof Fload created it.

### D6. A generated screenshot is not a published screenshot

The screenshot-localize route generates image bytes, uploads to object storage, updates a manifest, and inserts/updates recommendation/variant rows. Storage errors and DB errors are logged independently. No provider screenshot-upload execution was found in the inbox apply path; `update_screenshots` recommendations are advisory. The durable deliverable is a pinned image artifact and child ticket, not an invented store-publication receipt. [Screenshot generation/storage/handoff](https://github.com/fload-ai/fload-platform/blob/63275b2f51ac5b5a151a9a6683c813423e682785/apps/api/src/routes/assets/aso-screenshot-localize.ts#L433), [visual advisory proposals](https://github.com/fload-ai/fload-platform/blob/63275b2f51ac5b5a151a9a6683c813423e682785/apps/api/src/agents/implementations/aso-agent.ts#L5186).

### D7. Imported receipt provenance is not always reconstructible

The private aggregate census includes receipts without a surviving action FK, human-labelled receipts with no actor, system review receipts without tickets, sent drafts without readback bookings, and batches without content digests. These are migration categories, not automatic defect counts. A mirror of an external reply and a Fload delivery can have similar draft flags. Preserve original receipt IDs, known correlation references in a bounded, read-only migration ledger, observed timestamps, and unknown provenance. Do not manufacture approval or replay authority from an old `executed` label. Counts and source records remain private.

### Existing resource lanes

The source declares 15 central queues: `report`, `apptweak-report`, `report-pdf`, `setup`, `sync`, `sync-reports`, `valuation`, `scraping`, `email`, `alerts`, `review-sync`, `support`, `apptweak`, `apptweak-scheduler`, `inbox-iteration`; Agents adds `agent-execution`. Different connectors can address the same account/app; resolve canonical provider ownership before claiming. The current `work-verification` scraping job deliberately has no account group, so it receives only worker-wide concurrency. API/session/browser are transport facts on attempts. The active schema has **20 provider effects and four internal steps**, all closed in `action_step_kind`. Old review DELETE/CREATE phases are excluded from active dispatch and handled only in the cutover reconciliation checklist.

**Generation success requires one closed durable output.** `output_kind` is exactly `revision`, `review_analysis`, `agent_run`, or `no_work`, with mutually exclusive concrete fields. Draft generation and iteration name a sealed `output_revision_id` on the same ticket with `generated_from_revision_id` equal to the approved input. Analysis names the actual existing `review_analysis` row for the same organization/asset and a nonempty sample; this operation does not create a report version. Agent requests name the same existing agent run recorded at attempt start and require completed state plus correct organization/asset. Catch-up owns a collection-domain ticket from creation: request r1 produces sealed collection/post_batch r2 with concrete review children, or `no_work_reason=no_eligible_reviews` witnessed by its completed generation run. No empty review package or invented actionable request is needed.

Commit generated revisions, attempt result, settled execution, and the CAS of the current revision together; clear the current approval. A discarded stale candidate may retain an immutable revision without becoming the current head. Existing run/analysis artifacts remain authoritative in their own domains; the inbox stores strict foreign-key references rather than copies.

`next_run_at` is the sole durable due-time authority. A retry preserves the step's exact approved request; changing desired content requires a new sealed revision and approval. Provider-discovered chunk ranges are appended before I/O, reference the same approved immutable bytes, fit the pinned byte length, and cannot overlap. No credential-bearing upload URL belongs in inbox content.

**Release the resource guard when writes close, not when public verification finishes.** `writes_closed_at` is monotonic and requires evidence for all planned effects plus no unresolved write. It forbids further mutations and plan amendments. Readbacks can continue after the guard is released, so an App Store release wait cannot block all other app work for weeks. Old readbacks remain attached to their original revision and distinguish superseded state from a failed write. An expired worker lease alone never releases an uncertain provider write.

Store operations initially serialize per canonical account + app/package because a Play commit can invalidate another edit and Apple compound listing/App Clip work shares app state. ASA initially serializes per advertising account, a deliberately conservative boundary while single-target write/readback is established. This trades throughput for simple exclusion; narrowing it later requires an explicit hierarchy covering account, campaign and child resources, not invented app IDs or locks on local connector rows.

The application transaction acquires sorted action rows, execution rows, then canonical resource guards before authorizing an effect; trigger-level checks defend each invariant. No database lock is held during provider I/O. Stale workers append evidence; they cannot finalize current state or start another write. A policy-backed effect also locks its exact policy revision and refuses a missing or revoked grant; revocation does not block evidence for an already-issued request. Canonical services still establish current organization membership, credentials and scopes. Old receipts are retained by the bounded migration/archive plan and never gain authority to enter this active dispatcher.

## Strict retry and readback policy

No audited ASC, Play or ASA adapter sends a native provider idempotency key today. Local deterministic job IDs, single-use in-memory grants, duplicate scans and absolute-value writes do not establish native idempotency. A future `native_idempotency` mode requires endpoint-specific documented semantics and a contract test; default to readback or manual uncertainty.

`non_application_basis` is closed to `pre_dispatch_failure`, `provider_rejection`, `provider_terminal_non_application`, and `expired_uncommitted_edit`. A readback may claim final non-application only with a matching terminal provider request identity, or a proven expired owned Play edit that was never committed. No current adapter may invent a terminal-request contract. A plain negative read remains uncertain because a delayed request could still arrive.

| Observation | Allowed transition | Forbidden conclusion/action |
| --- | --- | --- |
| Validation/authentication/permission check fails before request dispatch | `known_not_applied` or typed `blocked`; record failure; retry only when gate clears | Do not mark provider success or consume a write budget for browser cooldown |
| Definitive provider rejection with known no-effect contract | `known_not_applied`; retry according to versioned policy and current authority | Do not assume every 4xx has identical semantics across multipart/multi-target operations |
| Timeout, connection loss, 5xx, malformed success response, worker crash after start marker | `uncertain`; due reconciliation read | No blind POST/PUT/delete retry; no browser fallback; no successor mutation while unresolved |
| Native idempotency contract verified and same exact step/request | Reuse same native key/body; retain each attempt | No reuse across steps, revisions or different request bytes |
| Complete read matches exact approved target/content | Append `matched`; resolve desired state, distinguish Fload acknowledgement vs external matching state | Do not fabricate provider request ID or say Fload created a resource merely because it exists |
| Complete read finds old content after ambiguous write | Wait per provider policy or manual resolution until late-write risk is resolved | A negative read at one instant is not proof an old in-flight request can never arrive |
| Partial page, missing field, unknown response state, inaccessible provider | `unreadable` with completeness reason; bounded next check or manual block | No absence claim; no default approval/success |
| Editable content matches but live still old | `saved/awaiting release` observation; retain required live follow-up | No `verified_live` until matching public evidence |
| Readback differs after a newer authorized revision applied | Record old-revision supersession and exact new execution relationship | Do not raise a false old-revision defect or revert newer copy |
| Different teammate/provider write changed baseline | `target_changed`; propose new revision or explicit resolution | Do not overwrite external edits merely because absolute-value PUT is repeatable |
| Lease expires but old attempt unresolved | Reconciliation claim only; append late evidence if received | Lease renewal/fencing cannot revoke a provider request |
| Provider acknowledgement succeeds and result DB commit fails | Pre-I/O attempt remains visible and uncertain; reconcile later | Do not convert post-write persistence failure into an ordinary failed write eligible for blind retry |

Missing provider-assigned IDs need an explicit recovery branch. If Play edit creation loses its response before the edit ID is retained, ordinary edit GET cannot be addressed from the known receipt alone; the adapter must prove a provider-supported discovery/finality path or hold visibly for reconciliation. Likewise, an App Clip reservation or upload chunk without adequate discoverable evidence must not be resent by a generic retry wrapper. These are provider contract test gates, not reasons to infer successful delivery or start a fresh plan silently.

The canonical resource guard serializes Fload writers, including different organizations addressing the same remote app. It cannot lock a person using the provider console. Where a provider offers no supported conditional-write contract, an external edit can race between baseline read and request; compare before writing, verify after writing, preserve attribution uncertainty, and surface conflicts. Database fencing alone is not an exactly-once or external compare-and-swap guarantee.

Apple listing readback already distinguishes editable from live and avoids a fabricated mismatch when content may be in review or awaiting release. Review readback already recognizes pending publication; preserve those meanings. Google Play developer-response verification is currently explicitly unsupported in Actions, even though Google's public API documents individual review reads and developer comments. Add a typed reader via existing authorized credentials or keep visible unsupported readback; the public API's existence does not prove Fload's current connector can access it. ## Commands, dispatch, cancellation and recovery sequence

1. Authenticate once at the canonical route boundary. Resolve internal organization member or exact system/policy identity. Runtime-validate the closed command and all tenant-scoped references.
2. Within one transaction, claim command idempotency key; compare request digest; lock/CAS current ticket and membership revision; check decision preconditions; persist approval, approver/policy, exact revision links, server-computed Undo deadline, execution, due time and history. Return the same receipt on retries. A changed request under the same key is a conflict.
3. Best-effort enqueue is a latency optimization after commit. A worker-owned reconciler scans due durable obligations with fair keyset pagination; it increments/uses a scheduling generation. It does not mark the business work failed because Redis is down.
4. A delivered envelope contains only a closed wire version, execution ID and scheduling generation. Resolve content from Postgres. Stale/terminal/foreign envelopes are no-ops/refusals. Recheck permission/entitlement/provider readiness where the approved contract requires it.
5. Lock the canonical resource and execution briefly; ensure no overlapping unresolved write; check server time against Undo; claim using generation/token; choose only the next eligible approved step; insert an attempt before network I/O; commit.
6. Perform one request under existing queue/account admission controls. Consume a newly minted content-bound grant at the real boundary. Persist per-request result and next due action atomically. The reconciler may restore the next wakeup after any crash.
7. For ambiguity, recover by readback; for success, check saved/live state as defined by the capability. Append observations. Finalize a step only from adequate evidence. Aggregate child and parent progress from authoritative records.
8. Undo and dispatch lock/CAS the same execution. Undo only before deadline and before any effect starts; record cancellation and invalidate queued generations. After work starts, Undo is rejected. A later stop/revert feature requires its own explicit command and semantics; it must not reuse Undo or conceal an uncertain effect. Reverting an applied effect is new reviewed work.
9. An admin retry, queue redelivery, reconnect, scheduled run or agent request recovery cannot bypass this protocol. No alternative writer updates lifecycle or grants approval from queue state.

## Data readiness, migration and operational acceptance

The candidate SQL was loaded into a fresh disposable PostgreSQL 17 database and its synthetic schema/provider proofs passed, including acknowledgement, uncertain readback, late evidence, generated-output linkage, and releasing a provider guard while verification remains pending. The combined harness also ran a real two-session row-lock/stale-snapshot conflict case. This validates those proposed relational invariants; it does **not** validate existing production migrations, BullMQ delivery/crash recovery, provider credentials, or real external writes.

The private DB census supports realistic fixture categories; it does not prove all historical identities, provider writes or timestamps. The final migration should output a private reconciliation ledger per source row with typed disposition: `converted`, `historical_only`, `needs_operator_resolution`, or `excluded_out_of_scope`. It must explain every row and refuse contract migration when active obligations remain unclassified. Do not write customer IDs/content into public artifacts.

Before cutover, collect a read-only rolling queue census of all 16 known queues, standard states, delayed jobs, repeatable schedulers, and Pro groups in waiting/limited/maxed/paused states. Standard `wait` length alone is incomplete. The provided `read-only-queue-census.mjs` uses read getters, skips queue metadata updates, has explicit sampling bounds, and emits only aggregate reference-presence statistics. It deliberately does not dump job payloads or error strings. It is an operational aid, not an atomic DB/Redis snapshot and not a repair tool.

Migration acceptance requires: source-row count parity by category; stable old URL/receipt identity resolution; exact content digest parity where provable; preserved rejection/history/run/experiment/media links; no inferred approval; no active receipt linked across organizations; no old pending mutation automatically requeued after ambiguity; all terminal/in-flight jobs drained, translated or fenced; recovery tested with Redis unavailable and all transport records removed in disposable test Redis.

Cleanup is explicit: remove the draft's send queue/lease counters and readback-booking authority, remove newest-unverified-row anchoring and mutable verification columns as current authority, remove retry wrappers for mutating requests, remove browser-held approval timers, remove personal lifecycle overlays, remove old approval adapters/worker consumers, remove embedded request-finalization JSON, and remove the dormant review queue only after census. Keep real agent runs, quota/capacity controls, provider parsers/comparators, experiment measurement, and unrelated outboxes. Do not recreate the removed private Pro-group-index cleanup.

Operational release gates: oldest due execution age and oldest uncertain attempt are observable; worker-owned reconciliation has independent watchdog and fairness; all actionable blocked reasons have an owner and next step; saved/live/uncertain are separately visible; provider readback coverage is explicit per adapter; no unknown enum or wire version is executable; all linked historical URLs remain usable. Full provider contract validation and isolated DB/Redis crash/migration tests remain required before implementation can be called production-ready.
