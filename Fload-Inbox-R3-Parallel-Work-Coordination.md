## Confirmed target policy: five items needing client attention

**Two different quantities (D1):** an **attention slot** is a ticket's current needs-client-action classification counted by the five-item cap. `attention_version` is the shared change counter used to calculate unread status; each user's `seen_attention_version` is their personal read watermark. The cap reads none of these read-tracking values or force_unread. A command can change slots without changing `attention_version`, or change that counter without changing slots. In this note, “slot delta” means the former; counter increments are always named `attention_version`.

This is an organization-shared admission rule, not personal unread state and not an execution concurrency limit. Derive it from canonical workflow plus the typed domain/prerequisite facts; do not store a second mutable needs_attention lifecycle boolean or infer it from free text.

| Current ticket situation | Attention slot | Required behavior |
|---|---|---|
| Actionable proposal awaiting a client decision | Yes | Exact current revision and actor authority; marking read does not free the slot |
| Approved; executing or passively waiting for provider/release progress with no client action required now | No | Keep visible as in progress/waiting, preserve approval, attempts and recovery |
| Client must now fix a prerequisite, decide a retry, edit or resolve a failure | Yes | Name the actual client action and owner, irrespective of whether the prior decision was approved |
| Fload/operator owns the next recovery step | No client slot | Surface to its responsible operator, retain honest status for the customer |
| Historical or completed work with no current decision | No | Preserve history and links; do not fabricate execution success |

**Existing wait projection (D4):** use the closed derived `waitRecoveryMode` from v15 §“Waiting presentation, real capacity and one recorded attention change,” with recovery availability evaluated using ownership v6's current cycle rules. For an otherwise eligible release/publication wait: `scheduled` or `automatic` contributes no attention slot; `recheck_required` contributes one and uses the existing-work exception when it becomes actionable. These are derived wire variants, never a new stored flag. Evaluate stronger obligations first: uncertain effects, permission/credential problems, evidence conflicts and a separately proved client-required prerequisite cannot be hidden by a future date or remaining automatic read capacity. A parent cannot hide a current child's independent decision. Merely offering optional controls such as Undo does not make passive work a required client action. Reuse that same projection in admission, detail, list and matching counts at one database asOf.

For other prerequisites, map the closed typed dependency and its responsible party into the canonical next-action contract. The current BacklogWorkValidationError.dependency is source evidence for that mapping, not a permanent second authority or permission to parse “Needs you”/“Blocked on us” text. Do not add provider-native enums to Core or reinstate v15's superseded grant storage.

“Editable release missing” alone cannot select a row of this table. If the client must create/upload a release, that is client-owned action. If a valid submitted release is processing and there is no client action required now, it is passive waiting. Domain/provider adapters supply closed, typed prerequisite facts; Actions owns workflow and consumes the provider-neutral next-action contract. Core gets no Apple-specific status or heuristic parser. The exact existing hold/owner variants must be reconciled in the remaining matrix; no unreviewed flag, table or new command is introduced here.

Example: two proposals need a decision and three approved tasks wait passively. A top-up may admit three proposals: **five attention items, eight unfinished tickets**. List/count endpoints expose the same canonical relation and name these scopes explicitly; eight total and five needing attention are different truthful measures, not an accidental mismatch. Future placement and snooze do not silently manufacture spare capacity; their effect must follow the same explicit actionability/date contract. Personal read/unread has no effect.

The five-item bound applies to **admitting new discretionary work**. It cannot prevent an existing approved task from developing an urgent blocker, an Undo from restoring a decision, or a known failure from appearing. Record and surface those changes even if attention temporarily exceeds five; pause additional suggestions until it drops below the limit. Never suppress a blocker on already-admitted work or block its evidence capture to maintain a cosmetic count. A refusal on a never-admitted suggestion follows the separate admission rule below; preserving its reason does not automatically authorize another client-facing card. This exception distinguishes truthful existing-work transitions from avoidable concurrent overshoot by new admissions.

No second numeric in-flight cap is selected. Approved waiting is still monitored and retains its owner, due/recovery obligations and stale-work visibility. Dependency groups/parent-child counting remain an explicit unit-design gate; sharing a prerequisite does not by itself prove multiple tickets are the same work.

### Manual commands and historical adoption (D3)

The cause of the change determines admission; the actor/channel does not provide an exemption. The review's suggested blanket human bypass is not adopted: it would make the same new work capped through an agent but uncapped through a manual top-up. The following matrix applies to authorized human, delegated, agent and system paths subject to their existing permissions. It creates no new permission.

| Transition | Admission treatment |
|---|---|
| New task/card; historical→work adoption by revise/edit; meaningful-change replace_declined; work declined/acknowledged→open restart | New discretionary work. When it increases occupied slots, require room under the shared guard, including for a present human |
| Historical unhide, placement or reconsideration that still results in a historical kind; evidence-only historical capture | No slot: history is excluded from current decisions. Do not reserve capacity or block these on the cap; later adoption independently checks it |
| Edit or placement of already-admitted open work without a slot increase; idempotent replay; proved zero/negative-net replacement | No additional capacity required; retain all ordinary command guards |
| Undo; newly actionable blocker/progress on an existing unfinished commitment; the eligible failed non-perform restore recovery; failed-perform recovery under its existing protocol | Existing-work exception. Compute/persist the true count under the same guard even above five; never deny recovery for lack of a suggestion slot. Prove prior admission and the current unresolved obligation from accepted command history; require exact current approval/execution lineage where applicable, including failed-execution restore and Undo. A preapproval blocker does not need a fabricated execution. Actor, old ID or prior approval alone does not establish this exception |
| Migration conserving already-admitted current work | Preserve the true existing population, even above five, under the fenced import protocol. The cap cannot erase or postpone conserved work. Historical activation after import is still new admission |

**Caller-minted command keys:** capacity refusal uses the existing immutable refused-command receipt structure, with proposed closed error value `client_attention_capacity` added consistently to Core, wire and persistence error enums. No arbitrary diagnostic payload, bypass flag, extra command kind or mutable capacity column is added. No head/kind/decision change commits on this refusal; any authorized preparation retains its truthful owner/usage records. Replay returns the original refusal after a slot opens; a new deliberate caller attempt needs a new key and fresh pins. This is not the contract for deterministic producer keys; use the next subsection. The rule is selected by the canonical producer entry point, never a caller-supplied bypass mode.

Historical matrix §2.1 and §3 apply this same rule. Human adoption at a full cap is a capacity refusal; human historical reconsideration alone is not. Work declined/acknowledged→open is a restart; approved work with the eligible failed non-perform execution is recovery. An edit to an existing commitment is not converted into a new admission merely because its author is human, nor is new work exempted because its ID already existed.

For example: both passes may prepare while the app has four tasks. The first transaction locks, re-counts four and commits the fifth. The second acquires the same guard, sees five and does not admit new work: it defers a deterministic producer offer without consuming its key, or records the ordinary capacity refusal for a caller-minted command. Preparation may be concurrent; accepted new work is serialized at commit.

The existing typed command matrix and lock-order integration still need implementation design and concurrency tests. This requirement adds no new table, generic job authority or open payload field.

The canonical internal producer-admission result is a closed union, separate from the existing user command wire response:

type ProducerAdmissionResult =
  | { kind: 'command_result'; command: ActionCommandResponse }
