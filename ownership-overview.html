01 / What changes

A different boundary, the same guarantees.

The latest design keeps the reliability work and changes who owns its rules.

Earlier proposed design · v15

A broad Actions contract

  • WorkflowDetailed policy mirrored across Core and SQL.
  • ProvidersNative fields and receipts partly consolidated in shared tables.
  • RecoveryInitial, event and Reconcile grants can coexist.
  • BillingSettlement and delivery fields extend the credit log.
Proposed ownership · v6

One workflow, explicit owners

  • WorkflowCanonical application policy; database constraints and atomic locks.
  • ProvidersTyped native targets, receipts and decoders in provider schemas.
  • RecoveryOne active bounded cycle per exact obligation.
  • BillingUsage owns settlement batches and a typed delivery outbox.

v15 was already a durable-ticket proposal. This change clarifies ownership; it does not promise fewer tables.

02 / Where things belong

Select an owner.

One database. Explicit schema and module boundaries.

Actions owns the decision and its history.

Permanent ticket IDs, immutable revision envelopes, exact approvals, bounded recovery and personal read state. Core does not interpret Apple fields or Stripe payloads.

05 / What is decided

A design direction, with explicit remaining work.

Ownership review resolved

Keep these boundaries.

  • Actions owns workflow; domains own content; providers own native contracts.
  • Approvals pin immutable revisions. Read state stays personal.
  • Commands and evidence are durable; unknown outcomes remain unknown.
  • Usage owns settlement and its typed delivery obligation.
  • Workers filter for supported contracts before claiming work.
Still open

Finish the exact contracts.

  • R2: corrected capture and race rules; finish exact provider codecs and structural constraints.
  • R3: 212 source fields inventoried; finish every typed destination, relationship and alias.
  • Complete final DDL, generated types and all required/forbidden field matrices.

Proof before cutover: migration conservation, real-role constraints, provider decoder fixtures, concurrency, retries, crash recovery and load tests. The older prototype is evidence, not the new DDL. Deployment mismatch is an operational issue, not a customer unread notification.

07 / How old data survives

Preserve what we know. Show what we don’t.

Every source record takes an explicit path. None becomes an approval or a success just because an old status says so.

Source → durable work

One identity. Exact content.

  • ConsolidateSources describing the same work resolve to one ticket. Real child work keeps its own ticket.
  • PreserveOld links survive empty batches, changed membership and missing original records.
  • AuthorizeHistorical approval stays in history. New execution requires a fresh, exact decision.
Source → history or a blocker

No guessed outcomes.

  • HistoryKeep actual actors, notes, content, timestamps and delivery claims with their provenance.
  • UncertainKeep the source and hold the migration when evidence is missing. Do not resend or invent completion.
  • RetryBlocked preflight can run again. Successful imports replay without creating duplicate work.

Latest safeguards: review sync cannot erase migrated history; leftover backlog cannot resurrect a deleted card; later drafts cannot override a rejection. Matching names, notes or timestamps do not prove a shared decision. Play numeric IDs need a proved package mapping. Retained domains still need strict schemas and converted readers.

Readiness: 212 source columns covered. No final table count approved. Exact destination DDL, historical-only work and alias shapes, plus data rehearsal and runtime tests, remain open.
