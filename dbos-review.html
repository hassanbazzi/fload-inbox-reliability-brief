Six concrete fixes before activation

R1–R4 have direct local reproductions. R5 is an unenforced migration assumption; R6 is a boundedness defect found in the caller and pinned SDK. No production loss or credential exposure was observed.

R1 · HighFailed work has no working repair

An ERROR wake cannot be resumed by the pinned SDK. The script only handles PENDING, and the promised alert path has no production caller.

Fix: Use a supported repair that revalidates current domain state, then prove alert → repair → recovery without another unsafe write.

Exact reviewed source ↗
R2 · HighSchema failures can expose credentials

The CLI receives DATABASE_URL in its arguments. On failure, the logged child-process error includes the password. A fake-password probe confirmed this.

Fix: Keep secrets out of command arguments where supported; sanitize every failure channel and regression-test the actual migration logger.

Exact reviewed source ↗
R3 · MediumDifferent IDs can produce one wake

Unescaped colons make distinct valid organization/execution pairs collapse into the same workflow ID. The second payload is silently ignored.

Fix: Use identical unambiguous encoding in SQL and TypeScript. Prove two scopes remain distinct and same-command retries remain idempotent.

Exact reviewed source ↗
R4 · MediumOperator repair escapes the queue limit

resumeWorkflow(id) defaults to DBOS’s internal queue. It bypasses the Actions queue’s configured concurrency. Normal same-slot startup preserves the queue.

Fix: Pass the Actions queue explicitly and test transfer from a removed executor with more jobs than its concurrency limit.

Exact reviewed source ↗
R5 · MediumExisting work is not adopted on upgrade

Existing rows receive wake_sequence = 0, with no initial DBOS wake. The design assumes no eligible executions exist, but does not enforce that assumption.

Fix: Either refuse unsupported populated upgrades or adopt due and claimed work transactionally, preserving original deadlines and approvals.

Exact reviewed source ↗
R6 · MediumOperator recovery reads the whole backlog

listWorkflows has no limit here, and SDK 5.0.2 has no default cap. Large failures become one unbounded memory load and serial operation.

Fix: Bound listing and recovery batches; test tied timestamps, interruption and changing statuses without skipped work.

Exact reviewed source ↗

Evidence, with its limits

Re-run and passed

  • 6 transactional wake-trigger tests.
  • 17 real DBOS worker tests across three suites.
  • 184 main + 13 metrics migrations, fresh and repeated; engine schema bootstrapped.
  • SIGKILL around provider boundaries, same-ID replacement, retained uncertainty and no second POST.
  • Active runtime drain with a gated provider response.

Still needs proof

  • Post-crash provider GET plus matching receipt: the current assertion can count an earlier GET.
  • Exact database time at first dispatch, not just “a visit occurred.”
  • Live overlapping replicas, operator transfer and incompatible version rollover.
  • Many long waits, retention, large backlogs and bounded repair pagination.
  • Current-head Semaphore CI and full provider/product cutover.

Provider HTTP is synthetic. Crash-child credentials and authority are substituted; canonical authorization is exercised separately by lifecycle tests. Four diagnostic probes confirmed defects and are not counted as four successful acceptance tests.
